## 0. 结论速览

| 问题 | 一句话结论 |
|---|---|
| **作用** | 四张牌：安全约束（已入仓）、匿名腿航迹（接口已导出）、场所几何源（grid.json 第四源，V2b）、SLAM 备料（PC 轨）。核心原则：**雷达产生约束与几何事实，不产生行为；有指向权，无声明权** |

## 1. 作用界定：权限分层，不是功能列表

### 1.1 四张牌（与既有文档的分工关系）

| # | 牌 | 权限性质 | 消费方 | 状态 |
|---|---|---|---|---|
| ① | **安全约束**：限速/停车/转向否决 | **约束权**（对已发命令做天花板，不产生新命令） | `rk_control.uart_send` 收口 | ✅ 已入仓（58 断言），待上车定标 |
| ② | **匿名腿航迹**：`person_legs[]` + Tracker | **指向权**（低置信传感器可指向、不可声明） | follow 的 BLIND/SEARCH、HRI | 设计就绪（`V2_LIDAR_FOLLOW_UPGRADE.md`），装车第一步验收=关联簇不否决转向 |
| ③ | **场所几何源**：墙/门框/开阔区 | **几何事实权**（替换手标 grid.json，消费方零改动） | `geometry_daemon` 第四源 `lidar`、`sector_score` HIDE 选点 | V2b（`V2V3_ROADMAP.md`），接口契约已定（避障 §5.4） |
| ④ | **SLAM 备料**：原始帧落盘 | 无权限（纯数据记录，机器人在线不依赖地图） | PC 科研轨 | `--record` 已有（2Hz 调参档）；全速率备料走 V2b"记录原始数据"行 |

**总原则**（三条文档共同收敛，本文重申为一条）：**雷达不决定"该不该跟、该不该让、去哪等"，只回答"以这个速度朝这个方向走会不会撞、周围有什么形状在怎么动、哪里有墙哪里有门"。** 行为语义归 follow/hri_state，身份归相机+模板，全局规划 V2 不做。

### 1.2 与其他传感器的分权矩阵（谁的领地谁负责）

| 感知需求 | 主责 | 雷达的角色 | 依据 |
|---|---|---|---|
| 谁是主人（身份） | 相机模板 + BLE 复核 | **永不放行**"跟陌生人"；只提供候选簇供相机复核 | 跟随升级 §0、§9 |
| 主人在哪（指向） | 相机（±32° 锥内） | 锥外 360° 腿簇 bearing——盲区时指向权完全归雷达 | 跟随升级 §2 覆写阶梯 |
| 前方多远有东西 | 超声（正前 ±15°，2cm 精度） | 360° 但稀疏；正前精度不如超声，两路独立取更保守 | 避障 §6 最后一行 |
| 门/墙/开阔区在哪 | 雷达（V2b 起替换手标） | 主责；相机 door_v3 做语义确认 | 底盘 §10.5 L1 |
| 距离保持（跟随 1.2m） | 编码器里程 + 相机框高 | `range_m` 接入后成为**可测的距离源**（V2b 后） | 跟随升级 §2 dist_fn |
| 人群密度/动态 | 雷达腿簇计数 + closing | 局部证据源；与手机 BLE 融合成分离风险分 | 本文 §4.4（新增挂钩） |
| 语义"是什么"（门 vs 家电 vs 人） | 相机 YOLO / YOLO-World 慢环 | 只给几何位置，不给类别 | V3a 语义网格规划 |
| 全局定位/地图 | **V2 明确没有**；V3 也无全局地图 | PC 轨离线吃日志 | 路线图总原则 2 |

## 2. 能力边界：三层量化（实测数据支撑）

### 2.1 物理层：实测数字 vs 文档假设

**数据源：本机 X3Pro 实测（2026-10-24，23 帧样本 @2Hz 录制 + 逐帧探针），对照三份文档的预设值。**

| 量 | 文档假设 | **实测** | 出入与含义 |
|---|---|---|---|
| 采样率 | 底盘 §10.5.1: 3000/s；跟随升级 §5: 4000/s | **≈2330/s**（233 点/圈 @10Hz） | ⚠️ 三份文档两个数，实测第三个数。**以实测为准**，推测驱动发布层有抽稀（SDK 原始率可能更高）——上板前用 SDK 直读验证一次 |
| 角分辨率 @10Hz | 0.9°/点（4000/s 假设） | **≈1.66°/点** | 腿命中数直接砍半，见下 |
| 12cm 腿命中点数 @10Hz | 1m/2m/4m = 7.6/3.8/1.9 | **≈4/2/1** | **腿通道在 10Hz 下 2m 外只有 1-2 点，宽度分类不可靠** → 证实跟随升级"腿通道建议 6Hz"（6Hz ≈ 0.99° → 7/3/2 点），且 4m 外腿检测本质边缘化 |
| 每帧有效点（0.24-8m） | 避障 §5.4 示例 412 | **72-88，中位 85** | 示例是 6Hz+空旷量级；10Hz 室内常态 85。`spike_dense_n=100` 门槛被踩线（飞点剔除多数时间不生效，避障附 D 已记） |
| 室内有效距离 | 标称 8m（12m 理想） | **P25=0.41 / 中位 0.49 / P75=1.35 / max 4.61m**（桌面环境） | 深色/吸光材质吃回波。**门框 2-6m 场景（底盘 §10.5 的选型理由）在真实室内只对高反表面成立**，白墙可期、深色门框存疑——装车后用 §2.3 验收第 2 条实测 |
| 帧率 | 5-10Hz 可调 | 10.0Hz 稳定（0.100s 精确） | ✅ 时延链假设成立 |
| 24 扇区密度 | — | 每扇区平均 **3.5** 有效点 | 15° 扇区统计有效；**不要做 ≤5° 粒度的扇区分析** |

### 2.2 数据层：噪声形态（桥/guard 已处理的不再重复）

- **无回波点**：驱动输出 `inf` 与 0.000x 毫米级噪点（实测确认）——桥过滤 + guard `range_min_m` 双保险；
- **镜面/玻璃穿透**：原理性无解，穿透时反而"有回波"（远处墙），`suspect` 模式不覆盖此 case——相机 door_v3 兜底（避障 §6 已列）；
- **飞点**：真实帧多数 <100 点 → 稀疏路径跳过剔除（附 D）；6Hz 提密度后此保护自动恢复；
- **同角双回波**：去重逻辑已入仓（避障 §4.1）。

### 2.3 语义层：雷达永远给不了的东西（重申+扩写）

身份 / 语义类别 / 玻璃与镜面 / 矮于扫描平面的物体 / 桌面台面悬挑 / 负障碍（下台阶）/ 高于平面的结构（人躯干、货架上半）。**单线雷达是"一个高度上的一圈轮廓"**，所有超出此模型的期待都是设计错误。V2 场景约束（不做下台阶、商场地面平整）把这些失效挡在产品边界外，写进能力清单而非藏起来（避障 §2.2 原则）。

### 2.4 ⚠️ 未决机械冲突：扫描平面高度，三份文档三个数

| 文档 | 高度 | 理由 |
|---|---|---|
| 底盘 §10.5（10-06） | **38cm** 后中独立支柱 | 高于篮口 30cm 无遮挡；仅桅杆 Ø1.2cm 遮 ~2.5° |
| 避障 §2.1（10-16，引 §15.7 决议） | **13.5cm** 夹层 | 坐在下层板小基座；自遮挡=4 铜柱各 ~2°（遮罩已自动算好） |
| 跟随升级 §5（10-16） | 建议**抬到 25-30cm** | 13.5=踝高，最易被椅腿/包/大衣吃掉；文献惯例 25-50cm（膝/小腿）；Moving Legs 非腿:腿 ≈ 3:1 |

**这是装车前必须收敛的 P0 决策**（直接决定：腿检测质量、铜柱遮罩参数 `pillars_xy`、`sensor_x/y`、是否新增支柱）。建议裁决方向：跟随优先 → 25-30cm 抬高（配合 6Hz）；结构/HIDE 优先 → 38cm 但腿通道降级为"近距兜底"。**裁决后统一三处文档 + 重算遮罩。**

## 3. 边缘落地清单：KickPi RK3566 上跑要注意什么

### 3.1 算力与内存（结论：富余，别自己吓自己）

| 项 | 数字 | 结论 |
|---|---|---|
| guard.update() 实测 | **0.47 ms/帧**（笔记本 CPU，110 点，含聚类/跟踪/迟滞/扇区） | A55 按慢 4× 估 1.9ms → @10Hz **占单核 ~2%** |
| daemon 轮询 | 20Hz 空转 + 读 1.7KB JSON | 可忽略；帧去重按 frame_id，空转无浪费 |
| /dev/shm 帧文件 | ~1.7KB/帧，原子替换 | 内存开销可忽略 |
| 板端内存总量 | 被 YOLO daemon + MJPEG 推流占大头（README：建图因此必须离线） | **这是"不上 ROS"的根因**，见 3.2 |

### 3.2 生产者路线决策：板上一律走路线 1（SDK 直连），ROS 只留 PC 轨

| | 路线 1：YDLidar-SDK aarch64（底盘 §10.5 原计划） | 路线 2：ROS 2 驱动 + 桥（已入仓，PC 验证用） |
|---|---|---|
| 板端内存 | SDK daemon ~30-50MB | ROS2 栈 +100-300MB、DDS 常驻 → **挤兑 YOLO**，不可接受 |
| 板端 CPU | <1% | DDS 发现/序列化常态 5-15% |
| 依赖 | 需 aarch64 交叉编译一次（PC 编好 sftp 推板，附 B-1） | apt 装 ros-humble-* 全家 |
| 硬件要求 | KickPi 是 Ubuntu 22.04 → ROS 得 Humble（非 PC 的 Jazzy），**又一处版本分叉** | — |
| 结论 | **上车正选** | PC 科研轨专用（桥已在仓，价值：无板调试整条链路 + SLAM） |

桥的契约转换三件事（方位角取负 / inf 噪点过滤 / ts 用 monotonic）**写 SDK 版桥时必须照抄**——已写进 `ros_scan_bridge.py` docstring 与避障 §5.1。

### 3.3 硬件与电气

1. **第三个 USB 口**：KickPi 已占 2 个（相机 + C3）。没有空口就加 ¥20 带供电 hub（底盘 §10.5 已预案）。**hub 要独立供电的**——雷达电机启动电流 + 相机 + C3 挂同一个无源 hub 是棕色重启的经典配方。
2. **供电域**：雷达 5V 挂**电子轨**（充电宝），与电机轨隔离（已决议）；X3Pro 整机 ~2.5W 量级，充电宝负载可忽略，但**开机时序**注意：README 已有"C3 偶尔不被识别，先开 KickPi 等 C3 灯亮再开电机电源"前科——雷达同鉴，开机自检脚本把 `/dev/ttyUSB*` 在列入 health_check。
3. **串口稳定性**：udev **by-id 别名**（照 `c3_controller` 先例写规则），别在代码里写死 `/dev/ttyUSB0`——相机/C3/雷达三个 USB 设备的枚举顺序不保证稳定。dialout 权限（板上是 root 服务则无所谓）。
4. **机械**：雷达电机是车上唯一持续旋转部件——**旋转异响/出圈断图**列为到手验收项（底盘 §10.5.1 前置检查 c）；装车后平面水平 ≤2mm（避障 §2.3 第 1 条），倾斜=远端假障碍环。

### 3.4 软件运维

1. **systemd 单元**：照 `imu.service` 模式（附 B-2），`Restart=always` + 崩溃退避；daemon 自身已带 stale/suspect 三态，systemd 管"进程死了"，`/safety` 的 mode 管"数据坏了"，两层互补。
2. **调度隔离**：YOLO 的前后处理在 CPU 上跑（11fps，NPU 只做推理）——建议 `CPUAffinity` 把雷达 daemon 钉在与 YOLO 不同的核，`Nice=+5`。guard 只有 2% 负载，这是防御性的，不是必须。
3. **别再踩的资源前科**：dnsmasq 99.7% CPU 自环（已修）、相机 USB autosuspend（已修 camera-usb-fix）——**雷达串口同样检查 autosuspend**（`usbcore.autosuspend=-1` 或对该设备 disable）。
4. **构建纪律**：YDLidar-SDK 版本锁定写进部署文档；X 系列串口协议直解作为 SDK 失败的 fallback（底盘 §10.5.1 前置检查 b）。
5. **度量纪律**（跟随升级 §8 全文有效，摘录三条上板即用）：passby 类场景 N≥5 取中位数报分布；任何"雷达有用"结论必须带关雷达对照组；仿真 HRI 拍改仿真钟。

## 4. 世界感知与理解的增量：五级阶梯

雷达能给"理解"的不是语义，是**结构**。按消费方成熟度排五级——**L1/L2 今天已产出，L3 是 V2b 的事，L4 是研究挂钩，L5 在 PC 上**：

### 4.1 L1 安全几何（已产出，消费方=避障收口）

`gap_m` 四向 / `rot_gap_m` / 24 扇区 / `escape`。机器第一次拥有"以我为中心的净空场"。**边界**：约束不是理解，它不知道"为什么这里空"。

### 4.2 L2 动态目标（已导出，消费方待接，V2b 步 2.5）

`person_legs[]` + Tracker 粘滞航迹 + `closing_mps`。机器第一次拥有"**周围有几个会动的形状、各在哪个方向、在靠近还是远离**"。这就是跟随升级的全部输入（BLIND→LED、SEARCH 朝空侧、夜景幻影否决、dist_fn）。**边界**：匿名——"哪条腿是主人"必须相机确认；2m 外点数不足（§2.1），越远越只剩"有东西在动"。

### 4.3 L3 场所结构（V2b：grid.json 第四源 → HIDE 选点升级）

现状：grid.json 8 扇区×3 环的 `free/blocked/obj:X` 由相机 edge_density + YOLO 产生，`sector_score` 在其上做 HIDE 交互亲和度打分（door-first、背墙、路中间惩罚——2026-10-11/22 两轮修过硬伤）。
雷达接入后：**360°×8m 的 free/blocked 环带一次成图**，替代相机"看见才有"的 60° 锥；门框（两个 blocked 夹一个 free 的模式）可从扇区序列自动提取，替换手标 doors。`geometry_map` 的 TTL=30s 滚动记忆恰好接住"跟随途中被动累积、HIDE 瞬间直接读"的产品语义。
**新增理解**：车第一次知道"我背后是墙"、"左边 3m 有个门洞"、"这片开阔区够我横移"。**边界**：扇区粒度 15° 是实测点密度决定的上限（3.5 点/扇区）；门≠语义门（自动门/玻璃门/开着关着仍要相机 door_v3 判）。

### 4.4 L4 相对导航与研究挂钩（分离风险的局部证据源）

`V2_PHONE_RELATIVE_NAV.md` 的三类"人不在视野"：(a) 侧后 0.5-2m 物理可见 → **雷达腿簇就是解**（转向指向+相机确认）；(b) 被挡 → 雷达+几何记忆选换视角路径；(c) 出范围 → V3 都不做。
**研究增量（本文新增挂钩，README 研究框架的直接落地）**："Pre-Separation: 人群密度上升 → 提前靠近"的**分离风险量化**需要一个局部人群证据源——`person_legs` 计数（周围几条腿）× `closing_mps` 分布（净靠近速度）× 扇区占用（可退空间）→ 一个可在线计算的 **crowd pressure 标量**，与手机 BLE RSSI（分离距离）融合即成分离风险分。**这个量相机给不了**（锥太窄）、手机给不了（无方向），只有 360° 几何能给——雷达在研究主线上不可替代的一格。

### 4.5 L5 PC-SLAM（科研轨，无死线）

rosbag 全速率 → slam_toolbox 离线建图（PC 环境已备）。产出物回流路径（底盘 §10.5 L2/L3 已画好）：静态地图 + 轨迹 → **若** V3 想要地图坐标系，车载只做轻量重定位（粒子滤波/scan-match，纯 Python 可写），RECEIVE 迎上才可能全局规划——**这是唯一超出"局部情境"总原则的预留口，且明确不在 V2**。
**诚实的预期管理**：商场/人群动态场景的 2D SLAM 会被行人污染（腿簇进地图成鬼墙）；缓解=会话级建图+动态点过滤（用 L2 的 Tracker 标记动点后剔除再配准）——这本身就是 PC 轨值得做的实验（§6 V-E4）。

### 4.6 增量总表

| 级 | 机器新知道什么 | 消费方 | 版本 |
|---|---|---|---|

## 5. 增量之外：明确不做（边界重申，防 scope creep）

1. **身份**：雷达永不声明"这是主人"——指向可以，放行不行；
2. **语义**：不说"这是门/这是柜台"——只给几何，类别归相机（含 YOLO-World 慢环）；
3. **玻璃/镜面/矮物/负障碍**：相机+超声+场景约束兜底；
4. **在线 SLAM/建图/重定位**：V2 机器人侧零依赖（路线图总原则 2），违者回读 3.2 的内存账；
5. **全局规划/A***：V2 不做；V3 只到"局部世界"，全局地图仍明确不做。

## 6. 验证计划（PC 轨本机可跑，全部带验收判据）

| # | 实验 | 方法 | 判据 |
|---|---|---|---|
| V-E1 | **腿检测距离曲线** | 人站 0.5/1/2/3/4m 各录 30s（10Hz 与 6Hz 各一轮），`--replay` 统计 person_legs 检出率与宽度方差 | 定出"腿通道可靠距离"（预期 10Hz:≤2m，6Hz:≤3m）；写回 §2.1 |

| V-E3 | **场所结构提取** | 房间+走廊 rosbag → slam_toolbox 离线建图 → 门框/墙位置 vs 卷尺实测 | 门框方位误差 ≤10°（8 扇区粒度内可用） |
| V-E4 | **动态场景退化** | 同一空间静止 vs 2 人走动各录一遍，离线建图对比 | 量化行人污染程度；验证"Tracker 标动点→剔除→配准"缓解有效性 |

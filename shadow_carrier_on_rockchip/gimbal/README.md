# Gimbal — 两自由度舵机云台（v2：C3 直驱方案）

摄像头两轴云台（Pan 水平 / Tilt 垂直）。**v2 架构：舵机由 ESP32-C3 的 LEDC 硬件 PWM 直驱**，
RK3566 只发角度命令，不再自己生成 PWM。

## 为什么放弃 RK3566 直接驱动（2026-08-22 实测结论）

| 原计划 | 实测结果 |
|---|---|
| Pan=GPIO4_A6(134) / Tilt=GPIO4_A7(135) | ❌ 软件能翻转，但**官方引脚图确认这两个脚不在 30pin 排针上**（万用表实测无任何脚跳动） |
| 排针其他 GPIO | ❌ 全被占用：GPIO3_C6~D7=音频I2S/PDM、GPIO4_A0/A1=PDM、GPIO4_A2/A3=uart7、GPIO4_A4/A5=uart9、GPIO1_A0/A1=i2c3 |
| 改 DTB 释放 16/18 脚 | ❌ p3/p4 是 U-Boot FIT 镜像（内核+dtb 打包+SHA256 校验），重打包变砖风险高 |

排针上唯一空闲的 GPIO 是 **28 脚（GPIO0_C6）**，只有一个不够用。
而 C3 Super Mini 空闲引出脚有 GPIO0/1/10/21（GPIO11 接内部 Flash，板上没有），足够。

## v2 架构

```
RK3566 (决策/视觉)                    C3 (执行)
gimbal_follow.py / rk_control.py ──USB CDC──> PAN <deg> / TLT <deg> 命令
        ↑ YOLO检测API(:8080)                  → LEDC 硬件PWM 50Hz → 舵机
```

- 舵机无编码器，**指令角即真实角**，无需回传；将来加 IMU/角度传感器走 `TEL:` 遥测行
- USB 全双工，C3 回显 `GOT:` / `PAN:xx.x`

## 接线（最终版）

| 舵机线 | 接哪 |
|--------|------|
| Pan 橙线 | **C3 GPIO0** |
| Tilt 橙线 | **C3 GPIO1** |
| 红 ×2 | 独立供电：电池(2S锂电7.4V)→二极管降压(~1.4V)或 mini360 模块调6V；MG996R 可容忍直连 |
| 棕 ×2 | 与 C3 **共地** |

⚠️ 不要用 KickPi 板载 5V 或 C3 板上电源带舵机（峰值 >1A，会电压跌落导致断连）。

## 固件改动（communication/C3_USB_Controller.ino）

- 新命令 `PAN <deg>` / `TLT <deg>`，超范围自动钳制，回 `PAN:x.x` 确认
- LEDC 50Hz @14bit（步进≈0.17°），兼容 arduino-esp32 2.x/3.x API
- 标定常量：`SERVO_PULSE_MIN_US=500` / `SERVO_PULSE_MAX_US=2500`，行程不对改这里
- 上电回中位 Pan=90°/Tilt=90°（1500µs 电学中位；机械正向偏移属正常，待标定）
- 烧录必须带 `CDCOnBoot=cdc`

## 凝视控制器（W1 已上线：救援式级联，2026-08-28 定稿）

> **A/B 实测结论**：GAZE_ENABLED=False（云台冻结）时 follow 稳定顺滑；
> 云台自动 pan 开启则底盘走偏/疯狂偏航。故云台在跟随中的角色从"持续追踪"
> 改为**"救援式视野保持"**——95% 时间冻结，仅在人接近出画边缘时出手。

### 状态机（KEEP/KEEP_TURN/HOLD/SEARCH/CENTER，全滞回）

| 状态 | 条件 | 行为 |
|------|------|------|
| KEEP | 人可见且光轴偏角 <24° | 云台冻结（follow 独占控制权） |
| KEEP_TURN | 偏角 ≥24°（接近出画） | 以 10°/s 缓转看住 |
| HOLD | 丢检 <1.5s | 冻结等待 |
| SEARCH | 丢检 1.5~4s | **定向扩展扫描**：记住人从哪边消失，朝该侧 10°→45° 递进扫 |
| CENTER | 丢检 >4s | 归中 90.58° |

### 底盘绞合（弧线转向，arxiv 1909.06087 同款架构）

云台偏 FORWARD 超 20° 持续 0.4s → 暂停 follow 的 DIFF，底盘以
DIFF L100/R70（或镜像）**弧线前进转向**（不是停车原地转）；回到 10° 内
归还底盘。超声波 BLOCKED 时倒车脱离（优先级最高）。

### 业界方案对照（2026-08-28 调研）

| 方案 | 与本项目的对应 |

### 实测教训（四条扰动通道，2026-08-28 A/B 实验定案）

云台持续追踪之所以搞坏跟随，是四条通道同时作用：
1. **新旧信号混叠**：转向误差=旧帧光学角+新云台角，云台一动两者时间错位（最高5°+假误差）
2. **误差吃光→猛扑**：云台把人保持在画面内→底盘看到的误差不足→不转→云台饱和/人出画→底盘猛扑
3. **幻影引发云台乱摆**：宿舍夜景 person 幻影（30s采样95/98帧含person, p最高0.91）被 largest-person 选中→云台追幻影→底盘跟着弧线撞凳子
4. **暂停揉面**：接管式设计的暂停/恢复循环（已废弃该设计）

对策：救援式（1/2/4 熄火）+ 注册门限55（3 的模板质量部分）+ follow 回退 person 过滤（3 的锁定部分）。
**遗留硬伤**：宿舍夜景幻影 person 率极高，最大person降级模式仍可能追幻影——根治依赖
owner 模板质量（穿鲜艳衣物）或更稳的 ReID，长期方案=码盘/IMU 里程计让"位置连续性"成为最强过滤。

## MPU 航向传感（已接入：KickPi I2C3，2026-10-04）

> 结论先行：直行走歪/弧线不准/偏航震荡三大痛全是**航向域**问题。
> 编码器+PID 治轮速域（距离），陀螺仪+PID 治航向域——先花 ¥5 治最痛的域。
> **架构落点已定：IMU 挂 KickPi（RK3566），不占 C3 引脚**（[统筹] 10-04 任务）。

### 实测状态（全部已验证）

| 项 | 结果 |
|---|---|
| 总线 | KickPi 30pin **pin16=SCL(GPIO1_A1)** / **pin18=SDA(GPIO1_A0)**；i2c3 原生启用，**免改 DTB** |
| 供电/接地 | VCC=pin1(3V3) / GND=**pin13**(或3/6/23/29，**注意 pin15 是 UART7 不是 GND**) / AD0→GND |
| 芯片身份 | `WHO_AM_I=0x70` → **MPU6500 类兼容片**（非正宗6050；寄存器兼容，**无 DMP**，本方案自算不用 DMP）|
| 数据 | 50Hz 稳定；静置噪声 **±0.06 dps**；4s 累积漂移 0.08° |
| **符号约定** | **从上往下看逆时针（左转）= `yaw_deg` 正**（实测约90°转角读数 92.5°，标度误差 +2.8%）|

### 读取器（零依赖）

- `scripts/imu_daemon.py` — 板上无 smbus 且无外网 → **直接 `/dev/i2c-3` + `I2C_RDWR` ioctl 裸读写**；上电静置校准 2s（零偏），EMA 低通 + 极慢泄漏积分
- 输出 `/dev/shm/imu.json`：`{ts, yaw_rate_dps, yaw_deg, gyro_raw, quality}`
- 启动：`sudo sh scripts/imu_start.sh --cal 2`（日志 `/tmp/imu_daemon.log`）；权限可用 `i2c` 组或 systemd `SupplementaryGroups=i2c`

### 已知边界（交底）

1. 兼容片**零偏温漂**比正版大：静置残差约 0.04 dps（≈2.4°/min）→ 短期跟随够用，**长期绝对航向需定期归零/温补**（未来）
2. 积分泄漏现设 0.25%/s（会缓慢拉向零）——长期航向用需调小；短期无感
3. TT 马达震动：模块需**刚性固定 + 泡沫胶隔振**（已叮嘱机主）
4. 控制环落点：IMU 在 RK → 航向 PID 在 **RK 侧**跑（50~100Hz），经 USB 串口(10~50Hz) 发 DIFF 给 C3；闭环带宽只需 1~5Hz，USB 延迟（5~20ms）可接受

## 2026-10-03 舵机事故与安全加固

### 事故链（三层定性，机主指正后记录）
- **根因=硬件**：舵机堵转/大角度电流尖峰 + 供电链脆弱；旧舵机反复跳齿后齿轮/电位器受损，形成"更易堵转"恶性循环
- **放大器=板级**：C3 掉电后 USB 不重新枚举的老毛病，把一次舵机事件放大成"遥控全失效"（网页活着、指令到不了 C3、舵机失声）
- **触发源=软件**：手动归中直跳 + `gaze.py` 的 `_wrap180` 误用（曾产生 -145°→固件钳 0→舵机全速甩到端点）；已修

### 软件加固（已部署 `6e6e809`）
- `gaze.py`：`_wrap180` 误用改为 `_clamp_pan`，运行限位 **15~165°**
- `rk_control`：`gimbal_send` 加限位 + 最近指令跟踪；新增 `gimbal_ramp_to` / `gimbal_center_ramp` **步进斜坡**；清除全部残留直跳（含 `/gimbal/center` 接口、凝视启动/退出）
- 进入/退出 follow 均步进到位，不再直跳

### 固件攒批新增（与 OBS 遥测一起烧；MPU 已落 KickPi，不在批次内）
- `servoInit` 斜坡化（上电不再直甩 90/90，治"上电咔咔"）
- 舵机脉宽收窄 500–2500 → **600–2400µs**

### WiFi 传输冻结
- `wifi/C3_WiFi_Controller/` 标记"已冻结 / 勿烧录"（机主拍板）：事故根因是舵机堵转电流，不是链路，换传输不解决

### 治本与证伪
- 治本 = 换舵机 + 舵机电源加 **470~1000µF** + mini360 **≈6V/≥2A**（独立于控制电源，仅共地）；软件护栏只降低复发概率
- **证伪实验**：换硬件后若"无咔咔却仍掉线" ⇒ 板级 USB 枚举缺陷独立存在，需单治或（demo 后）重新评估启用 WiFi 路线

### 运行限位不改几何标定
`PAN_MIN/MAX`、`TILT_MIN/MAX` 仅收紧**运行边界**，不改变 `PAN_FORWARD=90.58` / `TILT_LEVEL=112` 的几何标定值 —— [世界] 无需动作。
